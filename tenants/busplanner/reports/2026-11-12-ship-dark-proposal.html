Ship Dark, Release by Toggle

Separate merging code from releasing features. Code merges to main after review, switched off. One build is promoted unchanged from dev to stage to prod. An item is released when QA turns its toggle on, client by client.

Merge is not releaseUntested work ships dark. Nothing has to be reverted or frozen to cut a release.
One build, promotedStage and prod run the exact image QA tested. Our images and FE bundle already carry no environment config.
Release per clientWe are multi-tenant with a per-client flag table already. Turn a feature on for one pilot district first.

Default lane: merge dark

  • New screens, reports, endpoints, behaviour changes
  • Toggle named after the ticket, off by default
  • QA tests on CA dev with the toggle on for a QA test client
  • QA approval = toggle on in stage, then prod

Exception lane: QA before merge

  • Schema removals and renames
  • Auth, permissions, tenant scoping
  • Pipelines, infra, shared libraries
  • Tested on a QA environment, merged only when qa-approved

Guardrails

  • Toggle hygiene. Every toggle carries its ticket key and an expiry. Removing it is part of done. A cap on live toggles.
  • Off means inert. Review checks the off path. CI runs unit tests with all toggles off and all on.
  • Schema adds first. Additive migrations ship ahead of the feature. Removals go through the exception lane a release later.
  • Migrations in the pipeline. Timestamp ids instead of NN_, so parallel branches can't collide. MigrationTool runs in every deploy.
  • Toggles scoped three ways. Extend BPFeatureFlag (per client today) to global and per environment.

Getting there

  • At the GitHub move: main only, rulesets, build once and promote by SHA, hotfix from tag, aligned region defaults.
  • Next sprint: global and per-environment toggles, the two lanes, migrations in the pipeline.
  • After: per-client rollout as the normal release step, integration tests in CI.
