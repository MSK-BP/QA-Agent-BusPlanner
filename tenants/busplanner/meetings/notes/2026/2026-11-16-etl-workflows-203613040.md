## Rules and facts

- ETL Extract runs on the customer's Old World Windows server (SaaS or self-hosted) from Task Scheduler at about 2 AM and pushes SQL data as JSON to IBM Cloud Object Storage — stated — [10:39](https://fathom.video/calls/901422514?timestamp=639)
- Object storage has a dev, stage and prod instance, each with one bucket per client — stated — [32:10](https://fathom.video/calls/901422514?timestamp=1930)
- ETL Load is a cron job about one hour after Extract (for example 3 AM). It starts a pod from the `<env>-latest` image in the region's registry (US or CA), loads, then the pod ends — stated — [32:10](https://fathom.video/calls/901422514?timestamp=1930)
- The Old World plan is for today only. The ETL writes today plus the next days into `PlanSnapshot` (spoken as "plus nine days" and "plus 10 days"), and keeps past snapshots so a past day's plan can be read — stated — [27:16](https://fathom.video/calls/901422514?timestamp=1636)
- All table and column mapping from Old World (about 100+ tables) to New World (about 40 tables) lives in the ETL Extract code; no written mapping exists yet — stated — [21:49](https://fathom.video/calls/901422514?timestamp=1309)
- Each client has its own database; schemas are standard — stated — [42:02](https://fathom.video/calls/901422514?timestamp=2522)
- API backends run 1 pod in dev, 2 in stage, 3 in prod. Background services (substitution import, GPS readers) run as one pod with no multi-pod logic; a failed pod is restarted by the cluster — stated — [37:07](https://fathom.video/calls/901422514?timestamp=2227)
- The Unified GPS reader replaces the separate Old World Windows readers (Geotab, Synovia, GTS and others) and ingests coordinates and AUX signals (door, stop arm) — stated — [52:00](https://fathom.video/calls/901422514?timestamp=3120)
- New World product flags are per product per client (for example the chatbot flag); there are no per-feature flags, and behaviour is meant to be the same for every client — stated — [50:25](https://fathom.video/calls/901422514?timestamp=3025)
- Dispatch differs per tenant: some districts dispatch themselves, others use a third-party operator — stated — [04:33](https://fathom.video/calls/901422514?timestamp=273)
- The move to the New World is feature by feature and product by product, not one cutover — stated — [08:36](https://fathom.video/calls/901422514?timestamp=516)
- Discipline (Ride Support) spans web, driver tablet and the parent app (Chipmunk); it was "in really early stages" with no document yet as seen by the ETL owner — stated — [24:21](https://fathom.video/calls/901422514?timestamp=1461)

## Environments, access, release

- Branch flow (same as the Old World): feature branches off `dev`; a developer code review; merge to `dev`. All functional QA happens on `dev`, none on feature branches. The whole of `dev` is promoted to stage for regression; deployment goes through `main` — stated — [43:34](https://fathom.video/calls/901422514?timestamp=2614)
- No formal testing in production after a release; the deploying developer logs in and does basic checks after a deploy to dev, stage or main — stated — [45:53](https://fathom.video/calls/901422514?timestamp=2753)
- Bottleneck: a client fix sits in `dev` with many untested items; the choices are painful reverts or risky cherry-picks to stage — stated — [46:26](https://fathom.video/calls/901422514?timestamp=2786)
